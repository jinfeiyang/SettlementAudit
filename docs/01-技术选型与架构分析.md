## 1 总体架构设计

### 1.1 「双轨并行」逻辑架构

需求核心是 **确定性核算内核 + AI 语义判断双轨并行**：确定性内核"算得准"（CAD 矢量解析、清单标准化、定额/取费/工程量核查、重复计费识别），大模型"说得清"（语义对齐、疑点归因、报告成文）。系统按 6 层设计：

```
┌─────────────────────────────────────────────────────────────────┐
│ 展示层（PC 端） 内容管理/核查工作台/图纸可视化定位/报告编辑/台账  │
├─────────────────────────────────────────────────────────────────┤
│ 接入层  文件上传(DWG/DXF/Excel) · 统一认证(SSO) · 权限(RBAC)     │
├─────────────────────────────────────────────────────────────────┤
│ 应用服务层                                                       │
│  · 项目与资料服务    · 解析服务(CAD/清单)                        │
│  · 核查服务(定额/取费/工程量/重复计费)  —— 规则引擎驱动          │
│  · AI 服务(语义对齐/归因/报告)          —— LLM 网关 + RAG        │
│  · 疑点与报告服务    · 闭环服务(台账/规则反哺/标准库)            │
├─────────────────────────────────────────────────────────────────┤
│ 基础支撑  消息队列 · 任务调度 · 缓存 · 日志/审计 · 监控          │
├─────────────────────────────────────────────────────────────────┤
│ 数据层  业务库 · 解析产物库 · 定额/取费规则库 · 文件存储 · 向量库 │
├─────────────────────────────────────────────────────────────────┤
│ 基础设施  联通容器云平台(K8s) · 镜像仓库 130.36.8.236 · GPU 待确认 │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计原则**

1. **核算与 AI 解耦**：核查结论由确定性内核产出，AI 只补充语义解释与报告文字，独立服务、独立发布，保证"宁可少报不可乱报"的底线可审计。
2. **规则外置可配置**：定额、取费规则全部落库为可配置规则（规则表/DSL），支撑三期的"台账反哺规则库、标准库统一口径"闭环——规则库是产品级资产，不是写死在代码里。
3. **结论可追溯**：每个疑点记录来源（规则 ID、图元 ID/清单行号、AI 归因文本、人工复核状态），形成审计链。
4. **三期可演进**：一期模块化单体快速交付 → 二期按服务边界拆分 → 三期开放对接（与结算审计流程接口、全阶段扩展）。

### 1.2 部署架构（联通容器云平台）

- **部署平台**：中国联通容器云平台（K8s 集群 + 联通定制可视化界面），资源按 **租户-项目** 二级管理；本项目部署于「智创工坊-揭榜」租户（测试环境，比赛结束后如需保留再迁移），容器云访问地址 https://132.151.64.109。
- **镜像管理**：应用统一制作 Docker 镜像推送至联通容器镜像仓库 130.36.8.236:8443，基础镜像使用 `library/uos-server-20-1070u1a:latest`（UOS Server 20，较精简，缺依赖经 yum 临时源安装）。
- **数据库**：MySQL 由**省公司统一提供实例**，应用容器以连接串接入（不在容器内自建数据库）。
- **网络**：应用部署网段建议 132.151.74.0/24；涉及互联网/跨域/VPN 访问需走「打网申请」（业务流程系统3.0 → 权限类）。
- **认证**：接入联通 4A 平台统一认证（账号经申请），系统内按 RBAC 做造价人员/项目经理权限分离。
- **大模型**：首选元景 API；本地部署需容器云 GPU 节点支持（**待确认**），否则以 API 形态交付。
- **环境划分**：开发/测试（智创工坊-揭榜租户）→ 正式（赛后迁移）；配置外置、镜像统一、应用无状态化，保证可迁移性。

## 2 技术选型总表

| 层面 | 推荐选型 | 备选 | 选型理由 |
| --- | --- | --- | --- |
| 后端主框架 | Java 17 + Spring Boot 3.x（微服务组件：Nacos / OpenFeign / SkyWalking） | Spring Cloud 全家桶 | 联通企业级主流技术栈，团队可维护性强、生态成熟 |
| AI / 解析服务 | Python 3.11 + FastAPI（独立 AI 服务） | 与 Java 合并 | 解析（ezdxf/shapely）与 LLM 编排是 Python 强项，边界清晰 |
| 前端 | Vue 3 + TypeScript + Element Plus + ECharts | React + Antd | 联通常用前端栈，表格/表单/大列表场景成熟 |
| CAD 矢量解析 | **ODA File Converter（免费，DWG→DXF）+ ezdxf（DXF 解析）+ shapely（几何量算）** | ODA Drawings SDK（商业授权）；Aspose.CAD；国产 CAD 开放 API | 服务端批处理解析；免费起步、开源可控；商业 SDK 定位为精度/兼容性升级项 |

| 关系库 | MySQL（省公司统一提供实例，不自建） | 达梦 DM8 / 人大金仓（信创要求时） | 业务数据（项目/清单/疑点/报告/台账）；实例经云资源申请获取 |
| 解析产物存储 | 解析产物库：MySQL JSON 先行，量大后迁 PostgreSQL + PostGIS | ES + 对象存储 | 图元/块/标注/量算结果，PostGIS 支撑空间查询与回溯定位 |

| 向量库 | Milvus 单机版 | Elasticsearch（兼作检索） | 语义检索（图纸说明/定额特征/清单特征），支撑语义对齐与 RAG |
| 大模型 | **联通元景大模型（API 接入，数据合规首选）** | 内网 Qwen 系列（72B/32B）+ vLLM | 数据不出域；元景不可用则内网本地部署，禁止外部商用 API |
| 消息队列 | RocketMQ | Kafka | 核查/解析异步任务解耦、大文件处理排队 |
| 任务调度 | XXL-JOB | Spring 定时器 | 批量核查、报告生成、归档任务 |
| 缓存 | Redis | — | 规则缓存、核查结果缓存、会话 |
| 在线看图（图元回溯） | mxdraw（国产 Web CAD 看图，支持 DWG/DXF，可私有化部署） | 自研 Canvas/SVG 简化渲染（仅 DXF） | 需求要求"一键回溯至图纸图元位置"，前端必须可视化定位；**待验证局域网部署与授权** |
| 认证权限 | 联通 4A 平台（统一认证）+ RBAC | — | 角色：造价人员、项目经理（复核确认）分离；4A 账号经申请开通 |
| 交付物导出 | 报告/证书：Poi-tl（Word 模板）+ 预览 | 直接浏览器打印 PDF | 预审报告需成文交付（Word/PDF） |

## 3 关键技术决策点分析

### 3.1 CAD 矢量解析引擎（核心难点 1）

**需求约束**：服务端解析竣工图，读图层、块属性、标注，自动量算工程量；"不依赖仅靠识别的图像判断"。

**方案对比**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| ODA File Converter + ezdxf + shapely | 免费；命令行可批处理；ezdxf 生态成熟（图层/块引用展开/标注提取）；几何运算强 | DWG 新版本兼容依赖转换器版本；需每图纸走转换步骤 | **推荐（一期）** |
| ODA Drawings SDK | 直接读写 DWG/DXF 全版本，精度最高，业界标准 | 商业授权费用；C++/.NET 集成成本 | 升级项（需预算/精度硬指标时） |
| Aspose.CAD | 商业、跨语言 | 授权费、工程化自由度低 | 备选 |
| 国产 CAD 开放 API（中望/浩辰） | 信创合规 | 通常桌面级二次开发，服务端批处理部署重 | 不推荐，除非强制信创 |
| 纯图像识别（不能做） | — | 与需求"不做只靠识别的图像判断"冲突 | 排除 |

**推荐路线**：一期以 **ODA File Converter（免费）批量 DWG→DXF + ezdxf 解析 + shapely/networkx 量算** 起步，覆盖通信线路（线缆长度按图层/块路径量算）、设备安装（设备按块统计）两类典型工程；二期视实测精度与图纸版本覆盖决定是否引入 ODA SDK 商业授权。

**待验证事项**：① 图纸以 DWG 为主还是 DXF；② 是否存在加密、参照文件（Xref）、稀疏图层命名；③ 典型图纸的标注形式（线性标注/多行文字/属性块）。

### 3.2 大模型：接入方式、权限边界与误报控制（核心难点 2）

- **接入**：优先联通元景大模型 API；不可用则内网部署 Qwen 系 + vLLM；LLM 网关统一封装（模型切换、上下文组装、结构化输出 Schema、超时/重试、Tokens 审计）。
- **RAG**：向量库存定额规则、取费标准、图纸设计说明、清单项目特征，检索增强生成，回答带出处。
- **权限边界（硬约束）**：LLM 输出仅为"建议/解释/报告文字"，**不写库、不改金额、不置结论**；所有金额与结论类字段由确定性内核产出并需要项目经理人工确认，前后端均做校验兜底。
- **误报控制**：确定性规则为主，AI 语义仅为召回补充；三级疑点分级（高=确定偏差，中=疑似需人工复核，低=提示性）；分级阈值可配置；"宁可少报不可乱报"。
- **结构化输出**：统一 JSON Schema（疑点类型/级别/归因/依据引用），前端渲染，禁止直接输出自由文本结论。

### 3.3 规则引擎与规则库（支撑闭环反哺）

- 取费规则（基数、费率、工程类别匹配）、定额三级匹配（精确匹配→特征语义召回→换算系数校验）、重复计费规则均建模为**可配置规则**，带版本号与生效时间。
- 规则引擎选 LiteFlow 或规则表驱动：核查服务调用规则引擎，输出命中规则 ID 与偏差明细。
- **反哺闭环**：核减台账汇总 → 生成规则建议 → 人工确认 → 入库为新规则/修正规则 → 规则版本管理。（三期）
- 标准库（三期 ≥500 条全省统一口径）作为规则与口径的权威源，统一预审标准。

### 3.4 主技术栈整体取舍

| 决策点 | 决策 | 理由 |
| --- | --- | --- |
| Java vs 全 Python | Java 主业务 + Python 独立 AI/解析服务 | 联通合规与团队技能；AI 生态在 Python 侧，服务边界清晰、可独立演进 |
| 微服务 vs 单体 | 一期模块化单体（明确服务边界），二期拆微服务 | 一期工期极紧（见开发计划），避免微服务治理开销拖慢交付 |
| 数据库国产化 | 预留达梦/金仓切换能力（DAO 层与 SQL 规范约束） | MySQL 由省公司统一提供实例（不自建），应用按连接串接入 |
| 前端图纸查看 | mxdraw 私有化部署 | 满足一键回溯定位；不选 Autodesk Viewer 等云服务（数据出域风险） |

## 4 非功能设计要点

| 类别 | 设计要点 |
| --- | --- |
| 性能 | 解析/核查异步化（MQ + 任务队列）；大文件（图纸）分段处理与缓存；报告初稿 ≤10 分钟（AI 成文异步 + 结果缓存）；解析率/命中率指标埋点监控 |
| 安全 | 数据不出域；RBAC 权限（造价人员/项目经理）；操作审计日志（谁改了、改了啥、大模型是否仅解释）；文件访问控制与防下载策略（按需）；传输加密 |
| 可用性 | 核查任务失败重试与补偿；报告生成中间态可恢复；关键规则变更可灰度 |
| 可观测 | 规则命中率、AI 调用成功率、疑点误报/召回指标看板，支撑二期精度迭代 |
