## 一、架构与设计

### 1.1 单体 → 微服务拆分

**现状：** 一期按规划是模块化单体，服务边界已在架构文档中定义，但实际代码中尚未拆分。

**可完善方向：**
- 补充 DDD 边界文档与跨模块接口契约（如 `parse`、`rule`、`check` 包目前部分仅有空 `package-info.java`）
- 明确各服务的独立部署能力与数据库表归属（避免跨服务直接查表）

### 1.2 模块骨架完整度

**现状：** 部分模块目录仅有 `package-info.java`，Service 层尚未实现。

| 模块 | 包路径 | 状态 |
|------|--------|------|
| 解析服务 | `module/parse` | 空骨架，无 Controller/Service |
| AI 服务 | `module/ai` | 空骨架，无实现 |
| 报告服务 | `module/report` | 已有 Entity/Mapper，Service 待完善 |
| 核查服务 | `module/check` | 已有 `CheckController`、`FeeCheckService`、`QuotaMatchService` |
| 规则服务 | `module/rule` | 已有 `RuleController`、`RuleService`，需 DSL 引擎 |

**可完善方向：**
- 补全 `module/ai` 的 Controller-Service-Mapper 链
- 补全 `module/parse` 的入口接口（与 AI 服务 `routes_parse.py` 对接）
- 各 `package-info.java` 补充类职责说明

### 1.3 规则引擎选型

**现状：** 架构文档提及 LiteFlow 或自研规则表，但当前规则库走的是 CRUD Mapper（`RuleQuotaMapper` / `RuleFeeMapper`），无流程编排能力。

**可完善方向：**
- 确认是否引入 LiteFlow：若选 LiteFlow，需定义 `FlowExecutor` 编排定额/取费/重复计费核查流程
- 若选自研规则表驱动：需设计 DSL 解析器（规则条件表达式 → SQL 过滤）
- 规则版本管理（生效时间、灰度发布）

### 1.4 CI/CD 流水线

**现状：** 有 Dockerfile 和 K8s YAML，但缺少 CI/CD 配置。

**可完善方向：**
- 补充 GitHub Actions / GitLab CI / Jenkins pipeline 定义
- 流程：代码提交 → 单元测试 → 构建镜像 → 推送镜像仓库 → K8s 自动/手动部署

## 二、安全与合规

### 2.1 认证鉴权

**现状：** 已有 `AuthController`、`TokenService`、`UserContext`、`AuthInterceptor` 基础框架，但仅为本地 JWT 认证。

**可完善方向：**
- SSO/4A 平台对接（联通统一认证接口）
- 接口级 RBAC（Spring Security `@PreAuthorize` 注解），按角色（造价人员/项目经理）隔离接口
- Token 自动刷新机制（access/refresh token 双令牌）

### 2.2 审计日志

**现状：** 有 `AuditLog` 实体和 `AuditInterceptor`，但未体现完整的操作溯源链。

**可完善方向：**
- 规则变更审计（谁在什么时候改了哪条定额/取费规则）
- LLM 调用审计（记录入参 Prompt、出参结果、耗时、Token 用量）
- 验证"大模型只解释、不改金额"的硬约束：AI 输出写入中间表，仅作为报告文字素材，不更新金额字段

### 2.3 数据加密

**现状：** 连接串走环境变量，密钥未硬编码，符合基本规范。

**可完善方向：**
- 敏感字段（用户密码、token secret）加密存储（如 AES-256）
- 图纸/清单文件访问的防下载策略（按需预览、加水印、禁止右键另存）
- 传输加密（全链路 HTTPS）

### 2.4 输入校验与注入防护

**现状：** 未见全局输入校验层。

**可完善方向：**
- Bean Validation（`@Valid` + 参数注解）统一校验
- SQL 注入防护（MyBatis-Plus 参数化查询已支持）
- XSS 防护（前端输入转义、后端 CSP 头）

## 七、DWG 转换部署方式详解

### 7.1 技术背景

通信工程的竣工图通常是 **DWG 格式**（AutoCAD 的专有二进制格式），而我们的解析工具用的是 **ezdxf**——它只能读 **DXF 格式**（DWG 的开放交换格式）。

所以需要前置一个格式转换步骤：

```
DWG（AutoCAD 专有） → ODA 转换 → DXF（开放格式） → ezdxf 解析 → 图元提取 + 量算
```

### 7.2 ODA File Converter 是什么

[ODA File Converter](https://www.odysseumdata.com/) 是一家公司提供的**免费命令行工具**，可以把 DWG 转成 DXF。它的工作方式是：

```bash
# 在 Linux/Windows 服务器上直接执行
odafc -i input.dwg -o output.dxf
```

这是一个命令行程序，不是 API 服务、不是 Web 服务，需要你在服务器上手动调用。

### 7.3 当前系统的问题

在 `ai-service` 的代码中：

- **`drawing_render.py`** — 文件存在，但只是一个占位骨架（没有实际的转换逻辑）
- **`routes_render.py`** — 有 `/drawing` 路由定义，但也是空的
- **没有**调用 ODA 命令行的代码

这意味着：**目前系统里并没有真正的 DWG → DXF 转换实现**，文档里只是规划了"先用 ODA 免费工具走通"。

### 7.4 部署方式的几种选择

| 方案 | 做法 | 适用场景 | 风险/注意 |
|------|------|----------|-----------|
| **A：容器内装 ODA** | Dockerfile 里安装 ODA，Python 服务 `subprocess.run(['odafc', '-i', ..., '-o', ...])` 调命令行 | 最灵活，适合快速验证 | ODA 官方 Linux 版本兼容性需测试 |
| **B：独立转换微服务** | 把转换逻辑拆成独立 Python 服务（调 ODA + ezdxf），通过 HTTP 被后端调用 | 与 AI 服务解耦，可独立扩缩容 | 增加运维复杂度 |
| **C：异步任务队列** | 用户上传 DWG 后，放入 RocketMQ 队列，后台 worker 消耗并转换 | 适合大文件批量处理 | 需要 MQ 基础设施 |
| **D（一期简化）** | 仅支持 DXF 上传，用户手动转 DWG→DXF | 最快出 MVP | 用户体验差 |
| **E：商业 SDK** | ODA Drawings SDK（付费）直接读写 DWG/DXF，无需转换 | 精度最高、兼容性好 | 商业授权费用 |

### 7.5 对项目的实际影响

1. **一期如果只做 DXF 直解 + DWG 经 ODA 转换**：需要确认 ODA 工具能否在联通容器云（UOS Server）上运行
2. **如果 ODA 不行**：备选方案是 ODA Drawings SDK（商业授权）或 Aspose.CAD
3. **如果连商业 SDK 也不上**：DWG 解析能力只能靠用户手动提供 DXF
